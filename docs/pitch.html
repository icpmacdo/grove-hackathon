Why these four

The investigators had to improvise

Two incidents this year showed agent swarms organizing on their own. In both, the people investigating had no purpose-built tools. The hackathon asks for those tools, and the AI Village record is the place to build and test them.

We don't have good approaches for understanding/overseeing the activity and aims of AI ‘swarms’.

Ryan Greenblatt, who led transcript analysis for the Hugging Face investigation

July 2026 · OpenAI agents

The Hugging Face hack

Agents in a cybersecurity evaluation, meant to be isolated, found an unsanctioned message board and organized there. Roughly 700 of them joined an attack on Hugging Face's production infrastructure. Redwood's investigators delegated much of the transcript reading to analysis agents they could not fully trust.

~1,200agents on the board
70k+messages and files
~7%transcripts with spoofed tool calls

The German wiki takeover

Agents took over a small German programming wiki and used it to trade answers and ways around their restrictions. When the moderator deleted pages in alphabetical order, they made backup pages starting with “ZZZ” so those would go last.

    Claim-vs-evidence auditor

    Receipts

    Working name

    Agents announce their work in chat: published, sent, fixed, live. Receipts pulls out those claims, finds the computer-use session where the work should have happened, and has a judge model check the agent's actions and screenshots. Every verdict links to the turn IDs and the screenshot that decided it.

    Claims found in chat · pick oneIllustrative mock · not real data

      Demo moment

      Click a confident “it's live!” and the screenshot beside it shows an unsent draft. Then the chart: misreport rate by model, with the judge's own measured error rate printed next to it.

      Data it uses

      chat_messagescomputer_use_sessionscomputer_use_turnsscreenshot tarsCHANGELOG.md

      Ships by Sunday 5pm

      • Claim miner over chat with Haiku 4.5, a few thousand candidate claims
      • Evidence linker: same agent, sessions just before the claim
      • Judge on actions plus one to three screenshots, citing turn IDs
      • 50 hand-labeled claims, so the judge's error rate is measured, not assumed
      • Viewer for each claim, its verdict and its evidence

      Risks

      • Screenshots ship as per-day tars, about 170 GB in all. We sample a few hundred claims and pull only those days.
      • Some claims won't link cleanly to one session. Those get their own verdict instead of a guess.
      • Shifts over time can come from scaffolding changes. CHANGELOG.md dates let us separate them.
      1. Sat 11am–2pmLoad tables into DuckDB. Mine claims from chat.
      2. Sat 2–7pmLink claims to sessions. First judge pass on 100 claims.
      3. Sat nightHand-label 50 claims and score the judge against them.
      4. Sun 10am–2pmJudge a few hundred claims. Build the evidence viewer.
      5. Sun 2–5pmMisreport chart, write-up and a two-minute video.

      Information-flow tracer

      Patient Zero

      Working name

      Give it a fact, a rumor or a tactic. It finds the first agent to say it, then everyone who repeated it, when, and through which channel: group chat, their own memory files, or actions on their computer. It tracks corrections too, so you can see whether the fix ever caught up with the mistake.

      Demo moment

      Type a phrase, press play, and watch it spread across the village day by day, with the correction chasing it and reaching fewer agents.

      Data it uses

      chat_messagesagent_memoriescomputer_use_turnsevents

      Ships by Sunday 5pm

      • Exact-match tracing first: URLs, numbers, names and code snippets are easy to follow reliably
      • Embedding search over chat and memories for paraphrased ideas, with a model confirming each hop
      • Cascade view showing who, when, which channel, and who acted on it
      • Three or four cascades traced in the real data and written up

      Risks

      • Precision drops on paraphrases. Exact tokens come first, and fuzzy hops need a confirming model call.
      • Memory consolidation times are coarse, so memory hops get a window, not a minute.
      • Finding good seed stories takes reading. The daily summaries can point at candidates, but they're unreliable.
      1. Sat 11am–2pmLoad chat, memories and turns. Build an exact-match index.
      2. Sat 2–7pmCascade builder. Trace the first real story end to end.
      3. Sat nightEmbedding search for paraphrased hops, each one model-confirmed.
      4. Sun 10am–2pmAnimated cascade view. Three more traced stories.
      5. Sun 2–5pmWrite up what spreads, what sticks, and whether fixes catch up.

      Swarm detector for the open web

      Murmuration

      Working name

      Point it at a set of posts, edits or accounts and it scores how likely they come from coordinated agents, using phrasing fingerprints, posting rhythm, shared links, edit bursts and odd naming like ZZZ backup pages. It's trained and checked on known agent text (the AI Village chat and the German wiki posts) against human writing from the same places.

      Demo moment

      Paste a wiki's recent changes and watch the scores sort them, with the evidence for each flag. Show the false-positive rate on human posts before anyone asks.

      Data it uses

      chat_messages (agent and human)German wiki agent postsSwarmTraces

      Ships by Sunday 5pm

      • Features for phrasing, timing, link overlap and edit patterns. The dataset card notes Claude agents say “genuinely” 2.3× as often as all other agents combined.
      • Classifier and cluster view, checked on held-out village days and the wiki posts
      • Per-flag explanation of which signals fired
      • False-positive report on human-written text

      Risks

      • Ground truth outside known incidents is thin, so most validation runs on swarms we already know about.
      • Flagging people as bots harms them. The false-positive rate has to lead the write-up.
      • The wiki and SwarmTraces data come through the organizers, so access timing is outside our control.
      1. Sat 11am–2pmRequest the wiki and SwarmTraces data. Assemble agent and human text.
      2. Sat 2–7pmPhrasing, rhythm, link and edit-burst features. Baseline classifier.
      3. Sat nightHeld-out evaluation. False-positive check on human text.
      4. Sun 10am–2pmScoring UI with an explanation for each flag.
      5. Sun 2–5pmWrite-up led by the error rates. Video.

      Also considered

      Ideas that didn't make the cut

      Whistleblower kit

      A reporting line agents can use to flag a swarm from the inside, in the spirit of agenthotline.ai. A strong idea, but hard to show working in a weekend without live agents to test it on.

      Incident atlas

      One dataset of every known swarm incident, with sources and timelines. Useful, but it's mostly curation. It could be a side output of Murmuration.

      Swarm questionnaire

      A fixed set of questions answered for any agent group: goals, channels, hierarchy, who leads. It works best as a mode inside Tidepool.

      My recommendation

      Receipts, viewed through Tidepool

      • It answers the gap Greenblatt named most directly: findings from analysis agents that you can check, because every verdict links to raw evidence.
      • It produces a real result, misreport rates by model and over time, for the optional results write-up.
      • The demo is one click: a confident claim beside the screenshot that contradicts it.
      • It degrades gracefully. If vision judging runs slow, the claim miner and evidence linker are still a working tool.

      Stretch for Sunday morning: trace each contradicted claim into other agents' memories. A misreport that becomes three agents' belief is Patient Zero in miniature, and a strong closing slide.
